# Public deployment: the contract between its parts

The Guidance is installed and updated by `deployment/install.sh` (run in AWS CloudShell or on any machine with the AWS
CLI v2, Node 20+, python3 and credentials). Three parts, which only meet at the names below:

- **the CDK app** (`deployment/bin`, `deployment/lib`, `deployment/lambda`): the infrastructure;
- **the instance side** (`deployment/bootstrap/`, and in the build root `scripts/build-release.sh`,
  `scripts/package-bundle.sh`, `deploy/` public mode): builds and runs a release on the instance;
- **the installer** (`deployment/install.sh`, `deployment/installer/`): drives both from CloudShell. The one-click
  scripts `deployment/deploy.sh` and `deployment/cleanup.sh` only call it (The one-click scripts, below).

`<stack>` is the stack name (default `factoryos`, `[a-z][a-z0-9-]{0,30}`, not starting with `aws`, `amazon` or
`amzn`), `<region>` the stack's region.

## The layout and the build root
- The repository (and every archive of it) has the AWS Guidance layout: `deployment/` at the root, next to the
  Guidance's root files (`README.md`, `LICENSE`, ...) and `assets/images/`; everything else (the cargo workspace,
  `scripts/`, `deploy/`, `cell/`, `plan2cell/`, `web/`, `assets/`, `cell-planner/`, `rust-toolchain.toml`) under
  `source/`.
- **Build root.** On the instance, with the archive unpacked at `$src` (`/opt/factoryos/src/<version>/`):
  `tree="$src/source"` if `$src/source/scripts/build-release.sh` exists, else `tree="$src"` (the flat layout of an
  internal export, still supported). The release runs `$tree/scripts/build-release.sh`,
  `$tree/scripts/package-bundle.sh` and `$tree/deploy/factoryos-deploy.sh`; the target directories it prunes are
  `$tree/target`, `$tree/cell/target` and `$tree/plan2cell/target`. `deployment/bootstrap/` is always
  `$src/deployment/bootstrap/`.
- `install-build-deps.sh` does the same with `root=$here/../..`: it reads `$root/source/rust-toolchain.toml` (and
  `$root/source/plan2cell/rust-toolchain.toml`) when they exist, else `$root/rust-toolchain.toml`. Its `--stamp` mode
  works in both layouts and prints one line, `<sha256> rust <channel>[,<channel>…]` (the sha256 of the script and the
  toolchain files it read); `factoryos-release` skips the `deps` phase while `/var/lib/factoryos-release/deps.sha256`
  holds the same line. No toolchain file in either place: exit 1.

## VERSION.json
- Generated by the export (`scripts/export-public.py`) at the source root: `source/VERSION.json` in the Guidance
  layout, so `build-release.sh` and `package-bundle.sh` find it at their root, and the bundle carries it. There is no
  `VERSION.json` at the repository's root.
- `{"format":1,"release":"vX.Y.Z","tree":"<git tree id>","umarell":"<deploy/umarell.pin's commit>"}`: `release` only
  when the export is of a release tag (`vX.Y.Z`) of the exported commit, `umarell` only when the commit has
  `deploy/umarell.pin`. Public values only.
- Readers try `<root>/source/VERSION.json` first, then `<root>/VERSION.json`. In an archive, the file is the entry
  matching `^[^/]+/(source/)?VERSION\.json$` (the `source/` one first).

## The release archive and `<version>`
- An archive the installer accepts (`.zip` or `.tar.gz`) has exactly one top directory; inside it the repository
  root (with `deployment/`). Anything else is refused, by the installer and by the instance.
- **The release zip** of an export is `factoryos-<release>.zip`, with the one top directory `factoryos-<release>/`,
  plus `factoryos-<release>.zip.sha256` (sha256sum format: `<hex>  factoryos-<release>.zip`). Both are in the export's
  record next to its tarball. The installer checks an archive against `<uri>.sha256` when that exists.
- `<version>`, which names everything below: the archive's `VERSION.json` `release`; without one,
  `dev-<first 12 hex of the archive's sha256>`. For `--from-checkout`: the checkout's `release` (source/VERSION.json,
  then VERSION.json), else `git describe --tags --always`, else `dev-<sha12>`; a checkout with uncommitted changes
  gets the suffix `+dirty-<sha12>` (a sha256 over the packaged files). It matches `[A-Za-z0-9._+-]{1,64}`.
- An installer refuses an archive whose version is not the release of the tree it runs from (when that tree names
  one): run the `install.sh` of the archive you install.

## The installer's commands
```
install.sh install --from-checkout [--region R] [--stack-name S] [--users e1,e2] [--yes] [options]
install.sh install s3://<bucket>/<key>.zip|.tar.gz [--region R] [--stack-name S] [--users e1,e2] [--yes] [options]
install.sh status [--wait]
install.sh add-user <email>... | remove-user <email>...
install.sh uninstall [--snapshot] [--edge-only] [--confirm-stack <stack>] [--yes]
```
- `--from-checkout` packages the checkout `install.sh` runs from (the directory above `deployment/`): `git archive
  --prefix=factoryos-<version>/ HEAD` when it is a clean git checkout; otherwise a tar.gz of its files on disk with the
  same top directory, without `.git`, `node_modules`, `cdk.out` (and ignored files, `target`, `.venv`,
  `__pycache__`). It is staged in the work directory and uploaded with `aws s3 cp` to
  `s3://<source bucket>/releases/<version>.tar.gz`. An `s3://` archive is copied server side to
  `releases/<version>.zip` (or `.tar.gz`).
- `--stack-name` (also `--stack`) names the stack; `--region`, else `$AWS_REGION` / the configuration (printed, and
  confirmed unless `--yes`).
- `--confirm-stack <stack>` replaces the typed confirmation of `uninstall`, so it runs without a terminal; it must
  equal the stack name, otherwise nothing is deleted. Without it, `uninstall` needs a terminal. `--edge-only` deletes
  only `<stack>-edge` (the retry once CloudFront released the Lambda@Edge replicas).
- `--bedrock-models <id,...>` becomes `-c bedrockModelIds=<id,...>` and implies `--bedrock`. The installed options
  (`instanceType`, `volumeGb`, `bedrock`, `bedrockModelIds`, `kiroSecretName`, `umarellJam`) are kept in the SSM
  parameter `/factoryos/<stack>/install-options` (String, JSON) and reused by an update unless given again.
- `--umarell-tarball s3://<bucket>/<key>.tar.gz`: a `git archive --prefix=umarell/` of `deploy/umarell.pin`'s commit,
  copied to `vendor/umarell-<sha12>.tar.gz` of the source bucket (While sample-umarell is not public, below).
- `--umarell-jam-tarball s3://<bucket>/<key>.tar.gz | <local file>.tar.gz`: a `git archive --prefix=umarell/` of
  `deploy/umarell-jam.pin`'s commit (umarell_jam, below), checked as `--umarell-tarball`'s (a gzip tar whose first
  entry is under `umarell/`) before anything changes, and uploaded by the release step to
  `vendor/umarell-jam-<sha12>.tar.gz`. Its key and sha256 are the options' `umarellJam`: an update without the option
  sends the recorded one while `s3api head-object` finds it in the source bucket (else it warns and drops it);
  `--umarell-jam-tarball ''` drops it. With the version installed already (no `--force`) it is not used (a warning).
- `--build-project <name> --build-bucket <bucket>` (install only, together): the release is built in that AWS CodeBuild
  project instead of on the instance (Release build in AWS CodeBuild, below).
- `--rotate-origin-secret` (install only; with the version installed already too): a new origin secret; the backend
  restarts twice on the way (Origin secret, below). Without it an update keeps the installed one.
- **Region refusal.** Before any command, the installer reads `/factoryos/<stack>/edge-config` in us-east-1 (read only).
  If it exists and its `region` is not `<region>`, it refuses: that stack name is installed in another region, and
  deploying it here would point the first installation's sign-in at this one's user pool. Use the other region, or
  another `--stack-name`.

## Stacks
- `<stack>` in `<region>`: everything except the edge function.
- `<stack>-edge` in us-east-1: the Lambda@Edge function (`cloudfront.experimental.EdgeFunction`, `stackId`).
- CDK context the installer passes: `stackName`, `instanceType` (default `m7g.2xlarge`), `volumeGb` (default 200),
  `bedrock` (`true|false`, default false), `bedrockModelIds` (comma-separated inference profile ids such as
  `us.anthropic.<model>`, at most 20, no ARNs or wildcards; default: the agentic planner's profiles for the region, from
  `defaultBedrockModelIds` in `lib/config.ts`; only with `bedrock=true`), `kiroSecretName` (default empty), and
  **`amiId`** (required: the
  installer resolves the newest Ubuntu 24.04 arm64 AMI from the public SSM parameter
  `/aws/service/canonical/ubuntu/server/24.04/stable/current/arm64/hvm/ebs-gp3/ami-id` on install, and passes the
  running instance's own AMI on update, so an update never replaces the instance through a newer AMI).
- `kiroSecretName` set: the instance role may `secretsmanager:GetSecretValue` on that secret only. The secret's
  **name** reaches the instance through the `ReleaseDocument`'s environment (`FACTORYOS_KIRO_SECRET`, possibly
  empty; not through user data, so changing it never replaces the instance): every handoff writes it into
  `stack.env` (an empty name removes the key). The release (`factoryos-release`) reads the secret as root into
  `/etc/factoryos/kiro.env` (0600, `KIRO_API_KEY=…`; the secret may be the key itself or a JSON object with
  `KIRO_API_KEY`), removes that file when no secret is named, and never puts the value into CloudFormation
  parameters, user data, argv, the state or logs. The backend reads `kiro.env` (a systemd drop-in written by public
  provisioning); a secret that cannot be read or is not a key fails the release (before the build).
  **Not a boundary against the deployment's users:** every pool user is the workspace owner (`X-User-Alias:
  default`) and may open a terminal, a shell on the host as `factoryos` (the backend's user). The terminals leave
  `KIRO_API_KEY` out of the shell's environment (`WITHHELD_ENV` of `factoryos-pty`), but the shell reaches the
  instance metadata service (hop limit 1 stops only containers) and so has the instance role: one
  `aws secretsmanager get-secret-value --secret-id <FACTORYOS_KIRO_SECRET of /etc/factoryos/stack.env>` returns the
  key, and the same uid can likely read the backend's `/proc/<pid>/environ`. The Guidance README's security section
  says so; withholding the key from users would take terminals under another uid without IMDS access.
- Stack tag `factoryos:installer-format=1` on both.
- `bedrock=true`: the instance role may `bedrock:InvokeModel` and `bedrock:InvokeModelWithResponseStream` on those
  inference profiles in this account and region, and on the foundation models they route to only through them (a
  `bedrock:InferenceProfileArn` condition). Nothing else of Bedrock.
- **Stack descriptions and the Solution ID.** The Solution ID (`SO` and 4 digits) is null until the Guidance gets
  its id. Set it in two places, which must agree: `SOLUTION_ID` in `lib/app.ts` (the stack descriptions: both end
  with ` (SO####)`, `stackDescription`) and `solutionId` in `public-export/guidance.json` (the export's S6 check);
  `scripts/tests/test_export_public.py` (`SolutionIdTest`) fails when they differ.
- **The edge configuration.** The `EdgeConfig` custom resource of `<stack>` writes `/factoryos/<stack>/edge-config` in
  us-east-1 (String, JSON: `{"format":1,"region":"<region>","userPoolId","clientId","cognitoDomain",
  "distributionDomain","refreshTtlSeconds"}`) with `Overwrite: false` on create and `Overwrite: true` only on update,
  and deletes it with the stack. So a second `<stack>` in another region fails its create instead of taking over the
  first one's sign-in (and the installer refuses before that, Region refusal above). The stack names and the
  parameter's name never change.

## Source bucket
- Name chosen by CloudFormation (no fixed name). Block public access, SSL only, SSE-S3, versioned,
  `RemovalPolicy.RETAIN` = false (uninstall empties it first) — `autoDeleteObjects: false`.
- `releases/<version>.zip` or `releases/<version>.tar.gz` (`--from-checkout`, and `.tar.gz` exports): the exports.
  `vendor/umarell-<sha12>.tar.gz`: an optional umarell tarball (while sample-umarell is not public);
  `vendor/umarell-jam-<sha12>.tar.gz`: an optional umarell_jam tarball (the same).
  `releases/factoryos-viewer-linux-arm64-<version>.tar.gz`: the bundle of a release built in AWS CodeBuild (below).
- Instance role: `s3:GetObject` on `releases/*` and `vendor/*`, `s3:ListBucket` on the bucket (prefix-limited).

## SSM parameters (in `<region>`, not created by the stack)
- `/factoryos/<stack>/release/wanted` (String, JSON), written by the installer:
  `{"version":"…","key":"releases/….zip","sha256":"…","umarell":{"key":"vendor/….tar.gz","sha256":"…"}|null,
    "umarellJam":{"key":"vendor/….tar.gz","sha256":"…"}|null,"requestedAt":"<ISO 8601>","force":false}`
  (`umarellJam` absent is null: a handoff of this version reads an older installer's `wanted`.) A release built in
  AWS CodeBuild adds `"bundle":{"key":"releases/factoryos-viewer-linux-arm64-<version>.tar.gz","sha256":"…"}` (absent:
  the instance builds; the key must name `wanted.version`).
- `/factoryos/<stack>/release/state` (String, JSON), written by the instance:
  `{"phase":"…","version":"…","previous":"…|null","startedAt":"…","updatedAt":"…","finishedAt":"…|null",
    "error":"…|null","logStream":"…"}`, and on `ready` only, when there is any, `"incomplete":["umarell_jam",…]`: the
  names in `/etc/factoryos/provision-incomplete` (once each, in its order), optional parts the release was provisioned
  without (`umarell_jam`, `cell-planner`); `install.sh status` prints them (`incomplete: …`).
  `phase` ∈ `waiting` (no release yet) `downloading` `deps` `building` `packaging` `deploying` `checking`
  `ready` `failed` `rolled-back`. `version` is what the phase is about; `previous` the release that served before.
  `failed` with `version` "" is the first-boot setup's (user data, The instance below; `logStream`
  `<instance id>/bootstrap.log`).
  `error` (on `failed` / `rolled-back`): one line, at most 300 characters plus the rollback note: the step, its
  script and exit code, that script's own last error (`factoryos-deploy: …`, `provision.sh: …`; else the last
  error-looking line), then a failed unit's last journal error or an earlier script's error. Never provision.sh's
  informational `[provision] kiro agent file: …` line.
- Instance role: `ssm:GetParameter` on `wanted`, `ssm:GetParameter`+`ssm:PutParameter` on `state`, by their exact
  ARNs, no wildcard: `arn:aws:ssm:<region>:<account>:parameter/factoryos/<stack>/release/wanted` and
  `arn:aws:ssm:<region>:<account>:parameter/factoryos/<stack>/release/state`.
- `/factoryos/<stack>/install-options` (String, JSON), written by the installer, read only by it:
  `{"instanceType":"…","volumeGb":"…","bedrock":false,"kiroSecretName":"…","bedrockModelIds":"…",
    "umarellJam":{"key":"vendor/umarell-jam-<sha12>.tar.gz","sha256":"…"}|null}`.
- `/factoryos/<stack>/origin-secret` (SecureString): Origin secret, below.
- `uninstall` deletes these four after the stack, and `/factoryos/<stack>/edge-origin-secret` in us-east-1 (also on an
  `--edge-only` run once `<stack>-edge` is gone); a failure other than `ParameterNotFound` is a warning.
  (`/factoryos/<stack>/edge-config` in us-east-1 is the stack's own: the Stacks section.)
- `uninstall` also deletes the log groups Lambda created outside the stacks: it lists the stacks' functions
  (`list-stack-resources`) before deleting them, then deletes `/aws/lambda/<function>` (the CDK's custom resource
  providers, which have no LoggingConfig) in the stack's Region and, once `<stack>-edge` is gone,
  `/aws/lambda/us-east-1.<edge function>` (the Lambda@Edge replicas) in every Region of `ec2 describe-regions`.
- It then deletes the groups the main stack owns (`<stack>-CustomResourceLogs*`, `<stack>-VerifyAnonymousDenialLogs*`,
  `<stack>-VpcFlowLogs*`), listed from the stack before it is deleted, never derived from its name (a prefix of
  `<stack>-` also matches `<stack>-b-…`, another installation's). One of them comes back after CloudFormation deleted
  it: a custom resource logs while the stack is being deleted (EdgeConfig deletes its parameter) and Lambda delivers
  that line seconds later, which re-creates the group, empty and without retention. The sweep therefore waits
  `FACTORYOS_LOG_LAG_SECONDS` (default 30) first.

## SSM document `ReleaseDocument` (Command, no parameters)
Runs as root on the instance, returns within a minute: `deployment/bootstrap/release-handoff.sh`, inlined by the
CDK app (readFileSync at synth), written to `/run/factoryos/release-handoff.sh` and exec'd with bash, with the
environment `FACTORYOS_STACK`, `AWS_REGION`, `AWS_DEFAULT_REGION`, `FACTORYOS_SOURCE_BUCKET`, `FACTORYOS_LOG_GROUP`,
`FACTORYOS_PUBLIC=1`, `FACTORYOS_KIRO_SECRET` (possibly empty) and `FACTORYOS_BEDROCK=0|1`. It writes
`FACTORYOS_KIRO_SECRET` and `FACTORYOS_BEDROCK` into `/etc/factoryos/stack.env` (the other keys stay user data's;
the exported values win), writes `/etc/factoryos/origin.env` (Origin secret, below; a `wanted` with
`"secretsOnly": true` stops here, the state untouched), then reads `wanted`, downloads and checks the export into
`/opt/factoryos/src/<version>/`, installs that export's `deployment/bootstrap/factoryos-release.sh` as
`/usr/local/sbin/factoryos-release` and its `factoryos-release.service`, and `systemctl start --no-block`s it.
The unit does the rest and writes `state`. Refuses (exit 1, message) while a release unit is active.

## The instance
- Ubuntu 24.04 arm64, private subnet, no public IP, IMDSv2 (hop limit 1), SSM only (ssh masked).
- User data (`deployment/bootstrap/user-data.sh`, inlined behind a prelude exporting those six variables;
  **must not depend on the version**): writes
  `/etc/factoryos/stack.env` (`FACTORYOS_STACK=<stack>`, `AWS_REGION=<region>`, `AWS_DEFAULT_REGION=<region>`,
  `FACTORYOS_SOURCE_BUCKET=<bucket>`, `FACTORYOS_LOG_GROUP=<log group>`, `FACTORYOS_PUBLIC=1`), installs the AWS CLI
  v2 and the CloudWatch agent (shipping `/var/log/factoryos/*.log` to `LogGroup`, stream `{instance_id}/<file>`),
  creates 16 GiB swap, masks ssh, and writes `state` = `waiting` if it has none (or if it is a replaced instance's:
  its `logStream` names another instance id). While it runs, `reboot.target`, `kexec.target` and
  `ctrl-alt-del.target` are masked in `/run` only (`systemctl mask --runtime`), so an account's patch association
  cannot reboot the new instance in the middle of it; they are unmasked when it ends, on an error too. Not
  `poweroff.target`: a stop or terminate goes ahead. The agent ships `bootstrap.log` and `release.log` (the agent cannot
  name a stream after a wildcard's file, so the files are listed). Every step that needs the network (`apt-get
  update`, which fails on any index it cannot fetch, `apt-get install`, the two downloads, bounded by curl timeouts)
  retries every 15 s until 30 minutes after the start (`FACTORYOS_NET_WAIT`): a new instance behind a new NAT
  gateway has no way out for its first minutes. A failure is logged (`FAILED: …`, the command and its line) and,
  when the AWS CLI is there and no release ever ran, written to `state` as `failed` with `version` "" and
  `logStream` `<instance id>/bootstrap.log`; the installer stops on that state with its error. A run by hand after
  such a failure writes `waiting` again.
- The handoff downloads `wanted.umarell` to `/opt/factoryos/src/<version>.umarell.tar.gz` (a download or sha256
  failure fails the release) and `wanted.umarellJam` to `<version>.umarell-jam.tar.gz` (a failure there is a
  `WARNING` in the log, and the release goes on without it); `request.json` carries both (`umarell`, `umarellJam`:
  `{"path","sha256"}|null`), and `deploying` hands them to `factoryos-deploy.sh` as `FACTORYOS_UMARELL_TARBALL` /
  `_SHA256` and `FACTORYOS_UMARELL_JAM_TARBALL` / `_SHA256` (a missing umarell_jam file only warns). Both are pruned
  with their export.
- The handoff downloads `wanted.bundle`, when there is one, to
  `/opt/factoryos/bundles/factoryos-viewer-linux-arm64-<version>.tar.gz` with its `.sha256` (a download or sha256
  failure fails the release); `request.json` carries it (`bundle`: `{"path","sha256"}|null`), and `factoryos-release`
  goes from `downloading` straight to `deploying` (no `deps`, `building` or `packaging`), refusing a bundle whose
  sha256 is no longer the request's.
- Paths: exports `/opt/factoryos/src/<version>/`, bundles `/opt/factoryos/bundles/`, releases
  `/opt/factoryos/releases/factoryos-viewer-linux-arm64-<version>/`, `/opt/factoryos/current` →
  the running one. `/var/lib/factoryos/` (cells, catalogue, products, plans, umarell) is never deleted by a release.
- Modes: the backend and the planner router run the release as `factoryos`, so `/opt/factoryos`, `releases/`, every
  directory of a release and its `bin/*` are 0755 (files 0644) whatever umask created them: the SSM document runs
  under umask 077, and the handoff, `factoryos-release`, `factoryos-deploy.sh`, `provision.sh`, `build-release.sh`
  and `package-bundle.sh` each set umask 022 (a 0700 `/opt/factoryos` failed the backend with 203/EXEC "Permission
  denied", test install 2611122014-dc89; the handoff and `factoryos-release` repair one). `package-bundle.sh` fails
  on a directory or `bin/*` without r-x for others, and `factoryos-deploy.sh` refuses (`factoryos-deploy: error: the
  factoryos user cannot run …`, exit 1, the release before keeps serving) a release `factoryos` cannot run. The
  handoff's `state.json`, `request.json` and `release.log` are 0644 (no secrets); `kiro.env` and `origin.env` are
  0600 root, written so.
- Restarts: `/etc/needrestart/conf.d/90-factoryos.conf` (written by `factoryos-release`) keeps needrestart, which
  Ubuntu runs after every apt/dpkg run (a patch association's too, without `NEEDRESTART_SUSPEND`), from restarting a
  `factoryos-*` or `fos-*` unit; `factoryos-release.service` has `RefuseManualStop=yes` (no `systemctl stop` or
  `restart`; `systemctl kill` fails the release; a shutdown leaves it to the boot).
- Health (the `checking` phase, after the switch): `curl -fsS http://127.0.0.1/api/v1/health` (backend on
  `0.0.0.0:80`; the security group is the boundary), `factoryos-planner-router` active, and the planners' venvs
  importing what the planners need, run as `factoryos`: umarell's `.venv-planner` (pinocchio 3, ompl, langgraph, mcp,
  umarell's trajectory tools) always, and the cell planner's router venv (torch, mujoco, pinocchio, torch_geometric,
  its `tools.btexport`, `env.cell`) unless `/etc/factoryos/workspace.env` sets `FACTORY_OS_CELL_PLANNER=0`. The
  import lists are those of `deploy/provision.sh` and `deploy/provision-cell-planner.sh`; keep them in step. Any
  failure switches `current` back to the previous release (`rolled-back`), or, on a first install with no previous
  release, ends `failed`.
- umarell_jam (after those, when the release ships it: `deploy/planner-router/umarell_jam.py` and
  `cell-planner/umarell_jam/__main__.py` in the release, and `workspace.env` has no `FACTORY_OS_UMARELL_JAM=0`): its
  venv `/opt/factoryos-cell-planner/router/jam-venv` imports numpy, pinocchio, hppfcl, scipy, ompl and toppra as
  `factoryos`, with pinocchio at the cell planner's `requirements-umarell.txt` pin and toppra at `deploy/toppra.pin`'s
  (its cache keys depend on them), and `/var/lib/factoryos/umarell-<7 hex of deploy/umarell-jam.pin>/agents` exists
  (stamp: the pin's commit). **Never a health failure**: one that is not set up is a `WARNING: umarell_jam is not set
  up: …` line in the release log, `umarell_jam` in `/etc/factoryos/provision-incomplete`, the provision stamp
  dropped (the next deploy provisions again), and the release ends `ready` with `incomplete`. Its jobs then fall back
  to umarell_u3. `deployment/test/smoke.py` checks it for real (`python -m umarell_jam … setup`) and fails then.
- Release log: `/var/log/factoryos/release.log` (appended, one header line per release).

## Origin secret
The edge function adds `x-origin-verify: <secret>` to every request it forwards; the backend refuses, with it set,
every request from a peer that is not loopback without it. So the instance's port 80, which admits every CloudFront
distribution with a VPC origin for the instance (`CloudFront-VPCOrigins-Service-SG`), serves only this stack's
distribution, whose gate verified a session (threat model T-027). Defense in depth behind the security group, not a
user credential: every signed-in user has a shell on the instance (a terminal) with the instance role, which reads it
(the terminals leave `FACTORY_OS_ORIGIN_SECRET` out of the shell's environment, `WITHHELD_ENV` of `factoryos-pty`, as
they do `KIRO_API_KEY`; the instance role still reads the parameter).
- **The value.** 48 random bytes, base64url without padding (64 characters; readers accept `[A-Za-z0-9_-]{32,256}`).
  Made at deploy time, by the installer (python3 `secrets`, before the stacks) or by the stack's `OriginSecret` custom
  resource (`lambda/custom-resources/origin-secret.mjs`, on its create, when the installer did not make them first):
  never in the CloudFormation template, its parameters or custom resource properties (names only), the CDK context,
  the user data, an argv, a log or the state parameter. (CloudFormation's `AWS::SSM::Parameter` has no SecureString.)
- **Where it lives.** Two SecureStrings (the AWS managed key `aws/ssm`; standard tier); the installer writes them with
  `ssm put-parameter --cli-input-json file://<0600 file in a 0700 temp dir>` (deleted at once), `Overwrite: true`:
  - `/factoryos/<stack>/edge-origin-secret` in **us-east-1**: one value. The edge function reads it next to its
    configuration (`settings.json` `secretParameterName`, default: `parameterName` with `edge-config` replaced by
    `edge-origin-secret`) with `GetParameter` `WithDecryption: true` (Lambda@Edge calls SSM in us-east-1 like any
    Lambda; `aws/ssm` needs no key policy change), caches it with the configuration (5 minutes), and refuses (503)
    without a valid one. The edge-config String parameter is not made a SecureString: it is written by a CloudFormation
    custom resource whose input is template text. The edge role has `ssm:GetParameter` on exactly
    `arn:<partition>:ssm:us-east-1:<account>:parameter/factoryos/<stack>/edge-origin-secret` and on the edge-config
    parameter (`lib/edge.ts`).
  - `/factoryos/<stack>/origin-secret` in **`<region>`**: one value, or during a rotation two, comma-separated
    (`<new>,<old>`). The instance role has `ssm:GetParameter` on exactly
    `arn:<partition>:ssm:<region>:<account>:parameter/factoryos/<stack>/origin-secret`; nothing else reads it. The
    release document exports its name as `FACTORYOS_ORIGIN_SECRET_PARAMETER` (the handoff refuses another name).
- **When.** Before the stacks are deployed (install and update), the installer reads only their `Type` (and the instance
  copy's Description, Interrupted below): neither exists (a new installation, or one from before the origin secret,
  whose old backend ignores the header while the new release requires it): a new value into both, the edge's first;
  both: kept; the instance's alone: both anew; the edge copy alone: refused (another Region's installation of the name,
  or a leftover: the message names the delete command), as the custom resource refuses it. Either unreadable for another
  reason: the installer stops before any change. The custom resource keeps a pair it finds, and deletes both with the
  stack (its own physical id only); the installer's `uninstall` deletes them too (`ParameterNotFound` is fine).
- **On the instance.** Every run of the release document (the handoff, as root) reads `/factoryos/<stack>/origin-secret`
  with decryption (CLI stdout → python3 stdin → file) into `/etc/factoryos/origin.env` (0600 root,
  `FACTORY_OS_ORIGIN_SECRET=<value>[,<old>]`), and when that changed restarts `factoryos-backend` if it is active
  (the planner router, PartOf it, restarts too; a first install has no backend unit yet, the deploy starts it). Missing, not a SecureString, or not one or two base64url values: the
  handoff refuses (exit 1, the parameter named, never the value) before it changes anything. Public provisioning's
  drop-in (`deploy/provision.sh`, `factoryos-backend.service.d/public.conf`) loads `origin.env` with `kiro.env`.
- **The backend** (`crates/factoryos-backend/src/origin_verify.rs`, outermost around the router): with
  `FACTORY_OS_ORIGIN_SECRET` set, a request whose peer (the connection's address) is not loopback (127.0.0.0/8, ::1,
  ::ffff:127.0.0.0/104) needs exactly one `x-origin-verify` equal to one of the values (constant-time comparison),
  else `403` `Forbidden: not through this deployment's sign-in` (text/plain, no-store), WebSocket upgrades and the
  workspace prefix's redirects included. Loopback peers (the SSM port forward, the planner router, the release's health
  check, internal callers) are exempt. The header is removed before the routes (the proxies never pass it on). Unset
  (internal deployments, local runs): nothing changes. Set but malformed: the backend does not start (the error names
  the variable, not the value).
- **Rotation** (`install.sh install … --rotate-origin-secret`, after the infrastructure update and before the release):
  1. the instance's parameter := `<new>,<old>` (`<old>`: the edge's current value, read with decryption into python3),
     then the release document with `wanted` + `"secretsOnly": true` (origin.env written, the backend restarted; the
     `wanted` put back afterwards): the backend accepts both;
  2. the edge's parameter := `<new>`, then a wait of `FACTORYOS_ORIGIN_EDGE_WAIT` seconds (default 420: the edge's
     5-minute configuration cache plus a margin) until every replica sends `<new>`;
  3. the instance's parameter := `<new>`, refreshed again: `<old>` is refused from then on.
  No step leaves the edge sending a value the backend refuses. A replica whose configuration reload fails keeps its
  cached value (logged `config-reload-failed`) and is refused after step 3 until its next successful reload.
  It is not without downtime: each refresh changes origin.env, so the backend restarts twice (a few seconds each;
  `FACTORY_OS_ORIGIN_SECRET` is read at its start, there is no reload), the planner router (PartOf) with it, and the
  default `KillMode=control-group` ends the terminals' shells: open terminals close, `/zenoh` and `/chat` WebSockets
  drop and reconnect, a running planning job is stopped, and CloudFront answers `502` while the backend starts. The
  installer says so before it asks.
  **Interrupted.** The refreshes write `wanted` + `secretsOnly` only once the instance is ready, and an EXIT trap puts
  `wanted` back if the installer stops before it did (`run_release_command` returns an error, it does not exit):
  a `secretsOnly` request never stays (every later release document run would build nothing). A rotation that stops
  after step 1 (an error, Ctrl-C, a lost session during the wait) leaves `<new>,<old>` in the instance's parameter, so
  `<old>` stays accepted: the installer says "the old origin secret is still accepted; run install.sh install
  --rotate-origin-secret again", and later runs find the pair by its Description (`during a rotation: new,old`;
  `ssm describe-parameters`, the value not read): an update refuses unless it rotates, a run with the version
  installed already warns. Running the rotation again finishes it (its `<old>` is the edge's current value).

## Users
The installer creates and deletes users with `cognito-idp admin-create-user` / `admin-delete-user` (not
CloudFormation), only when `GateVerified` is `true`. The pool: native users only, no self sign-up, TOTP MFA required,
invitation message with the URL.

## umarell
- `deploy/umarell.pin` (in the build root): `<40-hex commit> <git URL>`. Public provisioning fetches that commit
  (`git fetch --depth 1`), or takes the `--umarell-tarball` from `vendor/` (checked by its sha256), into a plain tree
  `<umarell>-base` and a patched chat tree, each with a `.umarell.sha256` stamp.
- The chat tree gets the cell planner's series (`cell-planner/docs/upstream/patches_<id>/`), then **the public patches**
  `deploy/umarell-public/*.patch`, in name order (C collation), with `patch -p1 --forward --batch`; a reject or backup
  file fails provisioning. The base tree gets neither. The public patches' names and contents are part of the chat
  tree's stamp, so a changed patch re-provisions it. The export carries them (`+ deploy/umarell-public/**` in
  `public-export/manifest.txt`).
- `0001-trajectory-mcp-host.patch`: the trajectory planner's MCP server binds `TRAJ_MCP_HOST` (default `127.0.0.1`)
  instead of `0.0.0.0`.
- While sample-umarell is not public, an anonymous fetch of the pin fails and public provisioning stops with a message
  naming `install.sh --umarell-tarball`.
- **umarell_jam's umarell.** `deploy/umarell-jam.pin` (in the build root): `<40-hex commit> <git URL>`, the plain
  commit the planner router's umarell_jam patches (76ea13a). `deploy/fetch-umarell.sh --jam` installs it, unpatched
  and read-only, as `/var/lib/factoryos/umarell-<7 hex>` (stamp: the commit), from `git fetch --depth 1` or the
  `--umarell-jam-tarball` (`FACTORYOS_UMARELL_JAM_TARBALL` / `_SHA256`, checked by sha256 and `git get-tar-commit-id`).
  Optional: a failure, a private repository among them, marks umarell_jam incomplete (`provision-incomplete`) and
  provisioning goes on.

## Release build in AWS CodeBuild
`install.sh install --build-project <project> --build-bucket <bucket>` (the CloudFormation installer passes its
`<installer stack>-build` project and its inputs bucket, with `ReleaseBuild` `codebuild`, the default):
- After the confirmation and before the stacks, the export (the very archive the instance gets) is wrapped in a zip
  as its only entry, `export.zip` or `export.tar.gz` (a CodeBuild S3 source is a zip it unpacks), uploaded to
  `s3://<bucket>/builds/<version>-<sha12>/source.zip`, and the build is started with that source, the artifacts'
  path `builds/<version>-<sha12>` (name `out`, no packaging) and `RELEASE_VERSION`, `EXPORT_SHA256`.
- The project (Arm, `BUILD_GENERAL1_XLARGE`, `public.ecr.aws/ubuntu/ubuntu:24.04`: the instance's OS and
  architecture) checks the archive's sha256, unpacks it and runs its `deployment/bootstrap/build-bundle.sh <export
  dir> <version> <sha256> out`: `install-build-deps.sh`, `scripts/build-release.sh`, `scripts/package-bundle.sh
  out/bundle.tar.gz`, and `out/bundle.json` = `{"version","exportSha256","sha256","arch":"linux-arm64","builtBy"}`.
  An export without `build-bundle.sh` fails the build (set `ReleaseBuild` to `instance`).
- The release step waits for it (`FACTORYOS_BUILD_TIMEOUT_SECONDS`, default 5 h), refuses a `bundle.json` of another
  version, export or architecture, copies the bundle server side to `releases/factoryos-viewer-linux-arm64-<version>.tar.gz`
  of the source bucket and names it in `wanted.bundle`. A failed build fails the install (with its log link) before
  anything is sent to the instance; a build still running when `install.sh` stops is stopped (the EXIT trap).
- The instance role needs nothing new (`releases/*`). The project's role reads and writes `builds/*` of the inputs
  bucket only; a lifecycle rule expires `builds/` after 7 days.

## The one-click scripts
`deployment/deploy.sh` and `deployment/cleanup.sh` take no input: `AWS_REGION=us-east-1` and static parameters at
their top. They call only `deployment/install.sh` of the tree they are `deployment/*.sh` of (a clone, a CodeBuild
source), or, as standalone copies, of a fresh `git clone --depth 1` of `REPO_URL`: `install --from-checkout --yes
--region us-east-1 --stack-name <new name> --users <ADMIN_EMAIL>`, `status --wait` (with a deadline in bash, no
timeout(1)), then `uninstall --yes --confirm-stack <name>` and its `--edge-only` retries. `deploy.sh` never runs
`cdk bootstrap` itself (in `deployment/` the CLI synthesizes the app first, which fails without the installer's
context): it only checks that a `CDKToolkit` stack is absent or healthy, and `install.sh` bootstraps. With
`UMARELL_TARBALL=''` it stops before the install unless the pin's URL answers `git ls-remote` anonymously; with
`UMARELL_JAM_TARBALL=''` and a `deploy/umarell-jam.pin` whose URL does not answer it only warns, and a set
`UMARELL_JAM_TARBALL` becomes `--umarell-jam-tarball` (after `--umarell-tarball`). The stack
name passes from one to the other in `factoryos-oneclick.state` (`STACK_NAME=`, `REGION=`, `CLONE_DIR=`) in the
directory they run in. Their tests are in `deployment/tests/`.

The `ONECLICK_*` variables override their static values, as listed in `deployment/README.md`. Unset, the scripts
behave exactly as above.

## The CloudFormation installer (`pai-pd-installer.yaml`)

**Parameters:**
- `AdminEmail`
- `SourceMode` (`github` | `s3` | `upload`)
- `Release` (`latest` or a tag)
- `RepoUrl` (`https://github.com/<owner>/<repo>`)
- `ArtifactsUri` (`s3://bucket/prefix/`)
- `SourceArchiveUri`, `UmarellTarballUri` and `UmarellJamTarballUri` (`s3://` or `https://`; the last optional:
  without it umarell_jam is incomplete while umarell's repository is not public). `UmarellJamTarballUri` is part of
  `StartBuild`'s `Config` only when set (`|jam=<uri>` appended), so updating an installer stack to this template
  starts no build by itself.
- `AppStackName` (the `install.sh --stack-name`, default `pai-pd`)
- `InstanceType`, `VolumeGb`, `Bedrock`
- `ReleaseBuild` (`codebuild`, the default: the release-build project compiles the release; `instance`: the
  instance does). Part of `StartBuild`'s `Config` only when `instance` (`|build=instance`).

**The project's environment:**
- `ACTION` (`install`, the default; or `uninstall`), set per build by an override.
- `SOURCE_MODE`, `RELEASE`, `REPO_URL`, `ARTIFACTS_URI`, `SOURCE_ARCHIVE_URI`, `UMARELL_TARBALL_URI`, `UMARELL_JAM_TARBALL_URI`,
  `APP_STACK_NAME`, `ADMIN_EMAIL`, `INSTANCE_TYPE`, `VOLUME_GB`, `BEDROCK`, `INPUTS_BUCKET`, `RELEASE_BUILD`,
  `RELEASE_BUILD_PROJECT` (with `codebuild` the build script exports `ONECLICK_BUILD_PROJECT` and
  `ONECLICK_BUILD_BUCKET`, which `deploy.sh` passes as `--build-project` and `--build-bucket`).
- `WAIT_HANDLE_URL`, which only the create's build gets (an override from `StartBuild`).

**The artifact set:** files directly under one prefix.
- The export: `pai-pd*` or `factoryos*`, `.zip`, `.tar.gz` or `.tgz`.
- `umarell*.tar.gz`, optional (not `umarell-jam*`).
- `umarell-jam*.tar.gz`, optional: umarell_jam's (`ONECLICK_UMARELL_JAM_TARBALL`; an `https://` one is staged to
  `s3://<InputsBucket>/staging/umarell-jam-<sha12>.tar.gz`).
- Optional `<file>.sha256` files, whose first field is the hex sha256.
- An optional `artifacts.json`: `{"source": "<name>", "umarell": "<name>", "umarellJam": "<name>"}` (the last two
  optional), with names relative to the prefix and no `..`. When it is absent, more than one match of any kind is an
  error.

**Precedence:** an explicit URI wins over the artifact set, and the artifact set wins over GitHub. An uninstall
first uses `s3://<InputsBucket>/installed/<AppStackName>.{zip,tar.gz}`, which every successful install writes.

**The signal:** a `PUT` of `{"Status": "SUCCESS" | "FAILURE", "UniqueId": "install", "Reason": ..., "Data": <the
Url output>}` to `WAIT_HANDLE_URL`, with an empty `Content-Type`.

**Outputs:**
- `Url` and `GateVerified`, except with `upload`.
- `AppStack`, `BuildLogs`, `ReleaseBuildLogs`, `Uninstall` (the `start-build` command with `ACTION=uninstall`).
- `UploadTo` and `StartInstall`, only with `upload`.

Deleting the installer stack stops its running builds, the release build's too (`StopReleaseBuilds`). It never touches `<AppStackName>` or `<AppStackName>-edge`.
